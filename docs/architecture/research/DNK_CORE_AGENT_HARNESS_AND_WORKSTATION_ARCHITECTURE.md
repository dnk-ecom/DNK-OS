# 🏛️ DNK Core & OS: Архітектура Агентного Харнесу та Організації Робочого Простору на macOS

## 1. Вступ та Архітектурний Маніфест

### Фундаментальний парадокс Agent-First систем
При розробці автономних агентних систем інженерні команди зіштовхуються з жорсткою дилемою:
1. **Потреба в єдиному центрі управління (Control Plane)**: Оркестратор повинен мати доступ до загального контексту, довгострокової пам'яті (episodic memory), правил безпеки, черг задач і реєстру інструментів.
2. **Потреба в ізоляції компонентів (Execution Spokes)**: Якщо агенти, сервіси, плагіни та воркфлоу жорстко зашиті в ядро, будь-яка зміна ламає сусідні модулі, контекстне вікно моделі переповнюється сміттям (attention entropy), а локальне тестування вимагає підняття важкого моноліту.

**Рішення передових команд**: **Дворівнева Федеративна Архітектура (Two-Tier Federated Hub-and-Spoke)**, де **DNK Core** виступає суверенним **Control Plane / Harness**, а кожен агент, плагін чи сервіс є повністю автономним **Spoke-компонентом** із власним життєвим циклом, тестами, CLI та маніфестом.

## 2. Аналіз Світових Практик: Як Будують Передові Команди

### 2.1. Anthropic (Claude Code / Anthropic Agent SDK / Model Context Protocol)
*   **Архітектура Харнесу**: Claude Code та Agent SDK використовують модель **Dynamic Tool Discovery (JIT)**. Харнес тримає мінімальний базовий контекст (< 3,000 токенів на старті) і підвантажує схеми інструментів та навички (skills) лише за потреби через прогресивне розкриття (Level-of-Detail, LOD).
*   **Ізоляція інструментів (MCP)**: Жоден інструмент не живе всередині коду агента. Інструменти виносяться у зовнішні FastMCP сервери (stdio або SSE/HTTP). Агент спілкується з ними через стандартизований JSON-RPC протокол.
*   **Safety Hooks**: Контроль за діями здійснюється на рівні життєвого циклу харнесу: `PreToolUse` (перевірка дозволів та валідація параметрів перед запуском), `PostToolUse` (валідація результату, стиснення виводу перед поверненням у контекст).

### 2.2. Cognition (Devin) & OpenHands (SWE-Agent SOTA)
*   **Розділення площин**: Чітке розділення **Control Plane** (де живе планувальник, пам'ять та декомпозиція задач) та **Execution Sandbox** (де реально виконується код).
*   **Worktree-based Sandboxing**: На локальній машині чи віртуалці для кожного агентного завдання створюється ізольований `git worktree`. Це дає змогу агенту тестувати деструктивні команди, комітити та відкочуватися, не зачіпаючи основну робочу гілку розробника.
*   **Checkpoint & State Forking**: Харнес зберігає стан (файлові дельти, пам'ять, історію думок) перед кожною важливою мутацією. Якщо агент пішов хибним шляхом, харнес відкочує стан назад без перезапуску сесії.

### 2.3. LangChain / LangGraph & AutoGen / CrewAI
*   **Multi-Package Workspace**: Створюється монорепозиторій на базі `uv workspaces` (Python) або `pnpm workspaces` (TypeScript), де ядро (`core`) публікується як внутрішній пакет, а спеціалізовані сервіси імпортують його.
*   **State Graphs & Checkpointers**: Агентний процес описується як циклічний орієнтований граф станів (DAG з циклами), де стан зберігається у швидкій персистентній БД (SQLite WAL або Redis).

### 2.4. Nous Research (Hermes Agent / Gerych)
*   **Dual-Core Execution**: Поєднання легкого CLI-диспетчера (`hermes-cli`) та Gateway-сервера, який вміє керувати десятками протоколів (Telegram, Discord, Slack, Local TTY).
*   **SCONES Memory & RLM**: Довгострокова пам'ять винесена в окрему підсистему, яка підтягує асоціативні спогади за темою запиту, зменшуючи галюцинації та запобігаючи втраті контексту.

## 3. Топологія Репозиторіїв: Monorepo vs Polyrepo vs Federated Hub

| Критерій | Pure Monorepo | Pure Polyrepo | **Federated Hub-and-Spoke (DNK SOTA)** |
| :--- | :--- | :--- | :--- |
| **Context Window Footprint** | ❌ Критичне переповнення (агент бачить 100k+ файлів) | ✅ Мінімальне (бачить тільки 1 репо) | ✅ **Ідеальне**: Харнес бачить лише маніфести, воркери бачать тільки свій Spoke |
| **Git Conflicts & Locks** | ❌ Паралельні агенти блокують один одного в git | ✅ Повний нуль конфліктів | ✅ **Повна ізоляція**: Кожен Spoke — окремий git репозиторій або worktree |
| **Швидкість локального тестування** | ❌ Довгий CI/тест всього проекту | ✅ Миттєві ізольовані тести | ✅ **Суверенні тести**: `cd services/X && uv run pytest` за 0.8с |
| **Оркестрація та Керування** | ✅ Легко з одного кореня | ❌ Пекло координації (30 окремих вікон IDE) | ✅ **Централізований Кокпіт**: DNK Core керує всіма через MCP та сокети |
| **Версіонування та Релізи** | ❌ Синхронні залежності | ✅ Незалежні версії (SemVer) | ✅ **Повна незалежність**: Кожен сервіс має свій `pyproject.toml` / `package.json` |

> [!IMPORTANT]
> **Висновок для DNK OS**: Єдиний життєздатний підхід для сольного інженера чи високоефективної команди на MacBook — **Federated Hub-and-Spoke**.
> *   **Tier 1 (DNK_HUB / DNK Core)**: Центральний контрольний центр, стандарти, спільні типи, оркестратор агентів, реєстр плагінів.
> *   **Tier 2 (Spokes)**: Незалежні репозиторії або пакети для кожного сервісу (`dnk_shopify`, `dnk_media`, `dnk_distribution`), агентів та плагінів.

## 4. Фізична Організація Робочого MacBook (Apple Silicon + macOS APFS)

Apple Silicon та файлова система **APFS** мають унікальні переваги для агентної розробки, які світові інженери використовують для нульового оверхеду:

### 4.1. APFS Copy-on-Write (CoW) та Reflinks
*   Файлова система APFS підтримує миттєве клонування файлів і директорій без копіювання даних на диск (`cp -c` або Python `os.copy_file_range`).
*   **Практика**: Коли агент створює пісочницю чи робоче дерево для тестування важкого сервісу (наприклад, 2 ГБ даних чи картинок), створення пісочниці займає **15 мілісекунд** і споживає **0 байт** реального простору на SSD, доки у файли не будуть внесені зміни.

### 4.2. Нульове Дублювання Залежностей (Zero-Bloat Package Management)
*   **Node.js / TypeScript**: **Лише `pnpm`**.
    *   Глобальний стор: `~/Library/pnpm/store/v10`.
    *   Усі `node_modules` у кожному плагіні чи сервісі створюються через жорсткі посилання (hardlinks) на глобальний стор. 50 плагінів використовують рівно стільки ж місця на SSD, скільки один.
*   **Python**: **Лише `uv`**.
    *   Кеш: `~/.cache/uv`.
    *   Створення віртуального оточення через `uv venv` займає 100 мс завдяки клонуванню системних бібліотек через CoW.
    *   **Zero-Local-Venv Invariant**: Спільні рантайми тримаються у `~/.dnk_runtime/venvs/`, куди посилаються симлінки, або ізолюються через ephemeral-оточення.

### 4.3. IPC, Сокети та Керування Портами
Щоб сервіси та плагіни не конфліктували за порти `localhost`:
1.  **FastMCP over stdio**: Для зв'язку "Ядро ↔ Плагін" найкраще підходить `stdio`. Не потрібні мережеві порти, немає ризику застряглих сокетів, максимальна швидкість обміну даними (пам'ять ОС).
2.  **Unix Domain Sockets**: Для локальних фонових демонів (наприклад, база завдань, черга подій):
    *   Шлях: `~/.dnk_runtime/run/dnk_core.sock`
    *   Швидкість у 3-5 разів вища за локальний TCP loopback (`127.0.0.1`), повна безпека (права доступу регулюються файловою системою macOS).
3.  **Портова Сітка (Port Reservation Map)**:
    *   `3000 – 3099`: Клієнтські Web UI (Dashboard, Taskboard, Canvas).
    *   `8000 – 8099`: REST / GraphQL API шлюзи ядра.
    *   `9000 – 9099`: Зовнішні мікросервіси та сторонні вебхуки.

## 5. Анатомія Автономного Spoke-Компонента

Кожен сервіс, плагін чи агент розробляється як **самодостатня одиниця (Atomic Sovereign Unit)**.

```
services/dnk_example_service/
├── manifest.yaml             # ДНК компонента: версія, права, MCP-схеми, залежності
├── pyproject.toml            # Незалежні залежності (uv)
├── README.md                 # Документація та контракт
├── service.py                # Чиста бізнес-логіка (без прив'язки до LLM)
├── cli.py                    # Автономний термінальний інтерфейс (працює без ядра!)
├── mcp_server.py             # Тонкий адаптер FastMCP (експортує сервіс як інструменти для LLM)
└── tests/                    # Ізольовані тести (pytest / vitest)
    ├── test_unit.py          # Швидкі тести логіки
    └── test_contracts.py     # Тести відповідності контракту ядра
```

### Чому ця структура бездоганна?
1.  **Розробка без LLM**: Інженер або агент може зайти в директорію сервісу і запустити:
    ```bash
    python cli.py process --input data.json
    ```
    Він працює як звичайна CLI утиліта. Не потрібно піднімати всю DNK OS!
2.  **Підключення до DNK Core за 1 секунду**: Файл `mcp_server.py` огортає методи CLI в інструменти FastMCP. Ядро просто реєструє команду запуску у своєму конфігу:
    ```yaml
    # core_config.yaml
    mcp_servers:
      dnk_example:
        command: "uv"
        args: ["run", "--directory", "services/dnk_example_service", "mcp_server.py"]
    ```
3.  **Ізольований розвиток**: Оновлення версії бібліотек у `dnk_example_service` жодним чином не ламає залежності ядра чи інших сервісів.

## 6. DNK Core: Архітектура Головного Харнесу

Харнес — це "мозок і нервова система", а не виконавець завдань.

```
                    ┌─────────────────────────────────────────┐
                    │          DEVELOPER / FOUNDER            │
                    │   (Terminal, IDE, Canvas, Web UI)       │
                    └────────────────────┬────────────────────┘
                                         │
                    ┌────────────────────▼────────────────────┐
                    │               DNK CORE                  │
                    │         (Master Agent Harness)          │
                    ├─────────────────────────────────────────┤
                    │ 1. Gateway & Intent Router              │
                    │ 2. Context Engine (RLM / Sliding Diet)  │
                    │ 3. SCONES / Episodic Memory Bank        │
                    │ 4. Deterministic Quality Gates          │
                    │ 5. Task Graph & State Engine (SQLite)   │
                    │ 6. Tool Discovery & MCP Multiplexer     │
                    └─────────┬──────────────┬──────────────┬─┘
                              │              │              │
           FastMCP / Stdio    │              │ Unix Socket  │ Git Worktree
                              ▼              ▼              ▼
                    ┌──────────────┐ ┌──────────────┐ ┌──────────────┐
                    │  SERVICES    │ │   PLUGINS    │ │ AGENT SWARM  │
                    │ (Shopify,    │ │ (Web Search, │ │ (Denchik,    │
                    │  Media,      │ │  Figma,      │ │  Gerych,     │
                    │  Analytics)  │ │  Notion)     │ │  Auditor)    │
                    └──────────────┘ └──────────────┘ └──────────────┘
```

### Ключові Підсистеми Харнесу:
1.  **Gateway & Dynamic Router**: Аналізує ціль користувача, підбирає мінімальний набір інструментів та активує відповідного профільного агента.
2.  **Context Budgeter & Compactor**: Контролює, щоб у моделі ніколи не було більше 15-20k токенів активного контексту. Старі кроки згортаються у стислі дайджести, код читається тільки таргетованими слайсами (`view_file(StartLine, EndLine)`).
3.  **SCONES / Long-Term Memory**: Зберігає уроки, архітектурні рішення (ADR) та виправлені помилки. Перед написанням коду ядро витягує з пам'яті прецеденти.
4.  **Deterministic Quality Gates**: Харнес блокує прийняття результату агента на рівні системи (AST-перевірки, тести, відсутність тавтологій), запобігаючи голослівним заявам моделі.
5.  **Execution Sandbox (Worktree Manager)**: Для виконання складних задач харнес автоматично відгалужує `git worktree`, де агент пише код. Тільки після проходження всіх гейтів гілка зливається в робоче дерево.

## 7. Канонічна Структура Директорій на Робочому MacBook

Рекомендована еталонна структура для розміщення в домашній папці розробника (`~/Workspace/` або `~/Kuzmenko/MY_LIFE_WORK/`):

```
~/Kuzmenko/MY_LIFE_WORK/
├── .dnk_runtime/                       # [SYSTEM] Глобальний рантайм macOS (shared state)
│   ├── run/                            # Unix domain sockets (.sock), PID-файли
│   ├── logs/                           # Загальні логи виконання та аудиту
│   ├── venvs/                          # Базові спільні віртуальні оточення
│   └── cache/                          # Локальний кеш ембеддінгів та індексів
│
├── DNK_HUB/                            # [TIER 1] Control Plane (ЯДРО ТА ГОЛОВНИЙ ХАРНЕС)
│   ├── core/                           # Двигун харнесу: gateway, router, context, memory
│   ├── agents/                         # Декларативні маніфести агентів (Denchik, Gerych, Swarm)
│   ├── rules/                          # Інваріанти, правила поведінки (AGENTS.md, governance)
│   ├── contracts/                      # Спільні схеми: JSON Schemas, Pydantic моделі, протоколи
│   ├── docs/                           # Документація, ADR, звіти, база знань
│   ├── scripts/                        # Скрипти валідації (verify_all.sh), бекапів, лінтерів
│   ├── pyproject.toml                  # Конфігурація ядра (uv workspace root)
│   └── pnpm-workspace.yaml             # Конфігурація UI та веб-модулів ядра
│
├── services/                           # [TIER 2 - SPOKES] Автономні бізнес-сервіси
│   ├── dnk_shopify/                    # Сервіс Shopify: Liquid, Admin API, Theme Engine
│   │   ├── manifest.yaml
│   │   ├── pyproject.toml
│   │   ├── mcp_server.py
│   │   └── cli.py
│   ├── dnk_media/                      # Сервіс обробки та генерації медіа/відео
│   └── dnk_distribution/               # Сервіс маркетингу, дистрибуції та каналів
│
├── plugins/                            # [TIER 2 - SPOKES] Модульні плагіни та конектори
│   ├── dnk_plugin_figma/               # Плагін роботи з Figma API
│   ├── dnk_plugin_browser/             # Автоматизація браузера (Playwright/CDP)
│   └── dnk_plugin_notion/              # Синхронізація з базами знань
│
├── sandboxes/                          # [QUARANTINE] Ізольовані пісочниці для експериментів
│   ├── DNK_Vibe/                       # Зовнішні клоновані репозиторії для реверс-інжинірингу
│   └── scratchpads/                    # Тимчасові генерації та прототипи
│
└── themes/                             # [SPECIALIZED DOMAIN] Shopify теми та шаблони
    └── sovereign_themes/
```

## 8. Робочий Процес Інженера (Developer Loop)

### Крок 1. Створення нового агента або плагіна
Розробник хоче додати новий плагін `dnk_plugin_seo`:
1.  Створює папку `plugins/dnk_plugin_seo/`.
2.  Пише чистий скрипт чи бібліотеку на Python або TypeScript.
3.  Пише `cli.py` і переконується, що плагін працює локально:
    ```bash
    uv run cli.py audit-url https://example.com
    ```
4.  Пише 20 рядків адаптера `mcp_server.py` та `manifest.yaml`.

### Крок 2. Підключення до DNK Core
У `DNK_HUB/core/registry.yaml` або через автодискавері плагін з'являється у списку доступних інструментів.
Ядро тепер може делегувати задачі з аудиту SEO цьому плагіну, викликаючи його через FastMCP stdio.

### Крок 3. Автономне вдосконалення компонента
Якщо сервіс `dnk_shopify` потребує рефакторингу чи нових фіч:
*   Агент Denchik або людина запускають сесію безпосередньо в директорії `services/dnk_shopify/`.
*   Контекст моделі чистий: вона не завантажує код медіа-сервісу, ядро чи плагін Notion.
*   Тести проганяються за 1 секунду.
*   Після успішного коміту сервіс готовий до роботи з ядром без жодних змін у коді ядра.

## 9. Матриця Рішень для DNK Core (Actionable ADHD Summary)

> [!TIP]
> 1. **Репозиторна модель**: Тільки **Two-Tier Hub-and-Spoke**. DNK Core — це координатор (Tier 1). Сервіси та плагіни — незалежні репозиторії або незалежні пакети (Tier 2).
> 2. **Файлова система**: Активне використання можливостей macOS APFS (CoW клонування, `git worktree` для пісочниць, нульовий оверхед дисків).
> 3. **Залежності**: Тільки `pnpm` (жорсткі посилання на глобальний стор) та `uv` (миттєві віртуальні оточення без дублювання). Заборона важких некешованих інсталяцій.
> 4. **Зв'язок (IPC)**: FastMCP через `stdio` для плагінів/інструментів; Unix Domain Sockets для постійних фонових сервісів. Ніякого засмічення мережевих портів.
> 5. **Життєвий цикл**: Кожен сервіс має свій власний CLI, завдяки чому його можна розвивати, тестувати та дебажити ізольовано від ШІ-оркестратора.
