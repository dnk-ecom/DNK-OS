# Архітектура сканування бібліотеки репозиторіїв

Принцип: популярність (зірки) вимірює славу, а не корисність. Для загальних бібліотек слава
годиться як сигнал, для ніш (Shopify-теми, кодинг-активи, захист) ні: вони майже завжди мають 0 зірок.
Тому в нішах оцінюється **вміст**, а не слава.

## Шари

| Шар | Що робить | Мережа | Модуль |
|---|---|---|---|
| L0 Структура | дублі (обрізаний id), невідповідність URL, не GitHub, ключові слова ризику | немає | `curation.structural_flags` |
| L1 Метадані | існує, архів, ліцензія, push, зірки (1 запит на репозиторій, ETag) | GitHub REST | `repo_signals` |
| L2 Ніша | визначити, чи запис із ніші (за каталогом) | немає | `niche_profiles.detect_niches` |
| L3 Вміст | дерево файлів (1 запит), маркери домену, якість, шляхові ризики | GitHub REST | `content_scan`, `niche_profiles.analyse_tree` |
| L4 План | рівні KEEP / WATCH / QUARANTINE / REMOVE з причиною | немає | `curation.build_plan` |
| L5 Застосування | резервна копія, перенесення в карантин, відновлення | немає | `curation.apply_plan`, `restore` |

Правило ніші: якщо за славою запис потрапляє в QUARANTINE або REMOVE, і немає жорсткого ризику
(тайпсквотинг, накрутка, ключове слово), то він не видаляється за славою. Без L3 він стає WATCH
(`NICHE_PENDING_DEEP_SCAN`), з L3 оцінюється за вмістом: ≥60 KEEP, 35–59 WATCH, 15–34 QUARANTINE,
<15 або порожнє REMOVE. Підозрілі елементи дерева (`.env`, ключі, виконувані файли, лише архів)
відправляють у QUARANTINE для огляду людиною; у захисних репозиторіях виконувані файли очікувані
(зразки), тому там це не ознака ризику.

Дерево файлів безпечне: код не завантажується і не виконується. Це також межа методу: за деревом
не видно, що саме робить код, тому глибокий аналіз шкідливості (L6) лишається окремим кроком.

## Існуючі сервіси: що брати

Перевірено в цій сесії (читав сторінки): ecosyste.ms Repos, GuardDog, deps.dev. Решта нижче
з пошукових результатів і загальних знань, не перевірено на живих сторінках.

| Сервіс | Що дає | Що беремо | Обмеження |
|---|---|---|---|
| **OpenSSF Scorecard** (api.securityscorecards.dev) | автоматичні перевірки безпеки репозиторію (CI, підписи, залежності, пул-реквести) | L6-збагачувач для KEEP: підтверджена гігієна безпеки | покриває лише проєкти, які вже в їхньому індексі; сторінку в цій сесії не вдалося відкрити, ендпоінт треба перевірити |
| **deps.dev** (Google) | проєкти, дані Scorecard, поради безпеки OSV, залежності пакетів | ті самі дані Scorecard без своїх запитів; перевірка, чи репозиторій опублікований як пакет | орієнтований на пакети, а не на довільні репозиторії |
| **ecosyste.ms Repos** | метадані репозиторіїв багатьох екосистем, REST | масові метадані без квоти GitHub (5000/год на IP) | дані під CC BY-SA 4.0 (потрібна атрибуція), код AGPL-3.0: беремо лише дані через API, не код |
| **GuardDog** (Datadog) | виявлення шкідливих пакетів: правила Semgrep і YARA плюс метадані, оцінка ризику 0–10 | правила Semgrep/YARA як ідея для L6; сканування локальної теки | цілиться в пакети PyPI, npm, Go, RubyGems, GitHub Actions, VSCode; довільні репозиторії не охоплює |
| **OSS Insight** (PingCAP) | аналітика подій GitHub, колекції, рейтинги | перевірка трендів і «живості» за подіями | не перевірено тут; не заміна перевірці вмісту |
| **Software Heritage** | довгостроковий архів вихідного коду | порятунок: перед видаленням «мертвих» (404) записів перевірити, чи є архівна копія | не перевірено тут; не всі репозиторії заархівовані |

## Висновок

Готового сервісу «каталог + оцінка корисності для нашого домену» немає: усі вони міряють популярність
або безпеку пакетів. Тому ядро (L0–L5, вміст ніш) наше, а зовнішні сервіси підключаються як
необов'язкові збагачувачі:

1. **Software Heritage** для 219 «мертвих» репозиторіїв: якщо є копія, то вміст не втрачено.
2. **Scorecard через deps.dev** для KEEP із ліцензією: безпекова гігієна.
3. **GuardDog-правила** (Semgrep/YARA) як основа аналізу вмісту підозрілих записів, локально.

Збагачувач підключається як окрема функція `enrich(repo) -> факти` і додає прапорці, не змінюючи
рівні без перегляду людиною.
